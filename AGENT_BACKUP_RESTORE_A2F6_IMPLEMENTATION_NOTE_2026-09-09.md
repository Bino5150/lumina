## Findings repaired (Section 2 onward)

### B1 — Excluded-source inode identities can rotate during collection (BLOCKER)

**Root cause:** `forbidden_identities` (credentials, ledger.db) is resolved **once**, at the top of `build_agent_backup`, into a fixed `{label: (dev, ino)}` snapshot. Any inode that starts existing **after** that snapshot — a real secret-rotation event, or a hardlink retargeted to a brand-new file — can never be a member of it. AGENT-BACKUP-RESTORE-A2R6 proved this live: rotate `credentials.json` (or `ledger.db`) to a new inode, hardlink a state position to the *new* inode, and the alias sails through untouched. This is not a bug in the specific set of two forbidden identities this module happens to check today — it is a structural property of *any* fixed-snapshot blacklist: it can never account for an inode it didn't know about at snapshot time, including a future excluded source this module doesn't even define yet.

**Source-vet (Section 4, done before implementing):** grepped `core/`, `ui/`, `main.py` for `os.link(`/hardlink usage — no supported Lumina feature intentionally creates hardlinked durable state. Found a directly relevant, independently-arrived-at precedent instead: [`tools/file_edit.py:196-200`](tools/file_edit.py:196) already refuses to edit any file with `st_nlink > 1` (*"refusing to edit a hard-linked file (nlink=N): ... editing would silently detach it from its other links"*), and `tools/file_edit.py`'s own `_read_target_snapshot` (lines 98-112) already uses the identical `(dev, ino, size, mode, nlink, mtime_ns, sha256)` fingerprint-and-revalidate pattern this pass independently arrived at for B2 below. This is Lumina's own established house style for this exact class of concern, not an invented policy.

**Repair — categorical, not a wider blacklist:** [`core/agent_backup.py:1156-1164`](core/agent_backup.py:1156) `_open_state_bearing` now checks `fst.st_nlink != 1` on the already-opened, already-fstat'd descriptor, **after** the existing forbidden-identity check (so a credentials/ledger alias still reports the more specific, more actionable `"aliases the ... store"` reason; a hardlink to anything else — including a rotated identity a stale snapshot doesn't know about, or a completely unrelated ordinary file — reports the new, categorical `"is a hardlink (st_nlink=N)"` reason and outcome `kind='hardlink'`). `_stage_required_state_file` treats `'hardlink'` exactly like every other non-`'ok'`/`'absent'` outcome: `AgentBackupError`, fail the whole backup, never merely warn-and-exclude, for these REQUIRED, state-bearing positions.

This is a **policy escalation**, not an addition alongside the old policy: **A2R6 explicitly supersedes A2F5's own Section 11 "ordinary duplicate Agent state → captured independently, neither forbidden nor deduplicated" decision.** Under A2F5, two personas sharing one inode (both unrelated to credentials/ledger) archived independently and successfully. Under A2F6, the same setup now fails the whole backup — because this pass's own insight is that "ordinary" and "forbidden" cannot be reliably told apart from either name alone at any single point in time. `Canonical excluded paths remain excluded` (Section 6): `_EXCLUSIONS`/`_REGENERATE`/`_CANONICAL_CREDENTIALS_EXCLUSION`/`_CANONICAL_LEDGER_LOGICAL_ID` and `_resolve_credentials_identity`/`_resolve_ledger_identity`/`_build_forbidden_identities` are **unchanged** — the nlink invariant is an *additional* filesystem boundary, not a replacement for the manifest-semantics exclusions.

**Scope decision, recorded:** the nlink check lives only in `_open_state_bearing` (the strict, required-state-bearing boundary) — **not** in `_open_verified` (the lenient boundary still used for genuinely optional members: `identity_trailers.json`, `codebase.md`), and **not** applied to SQLite sources (`lumina.db`/`flight_recorder.db`), which are captured via `_snapshot_sqlite`'s own online-backup-API + `_connect_sqlite_with_bound_identity` mechanism — already independently hardened (A2F3/A2F4) and re-cleared (A2R5), explicitly out of scope per the mission's own Section 29 ("No SQLite redesign") and Section 5's hardlink matrix, which does not list either database. Confirmed by static assertion (`test_stable_capture_never_applied_to_sqlite_sources`) that `_snapshot_sqlite`'s own source never references the new primitives at all.

**Regression:** `test_ordinary_duplicate_agent_state_hardlink_now_fails_closed` (rewrites the now-superseded A2F5 test), `test_new_overlay_member_hardlinked_to_ordinary_file_fails_whole_backup` (parametrized: skill, tool_profile, avatar, voice), `test_custom_tool_hardlinked_to_ordinary_file_fails_whole_backup`, `test_tool_audit_log_hardlinked_to_ordinary_file_fails_whole_backup`, `test_pending_actions_json_hardlinked_to_ordinary_file_fails_whole_backup`, `test_project_binding_json_hardlinked_to_ordinary_file_fails_whole_backup`, `test_project_chats_json_hardlinked_to_ordinary_file_fails_whole_backup`, `test_prefs_json_hardlinked_to_ordinary_file_fails_whole_backup`, `test_projectlist_md_hardlinked_to_ordinary_file_fails_whole_backup`, `test_state_bearing_hardlink_open_returns_hardlink_kind_directly` (direct unit proof). All pre-existing credentials/ledger hardlink tests (`test_state_bearing_hardlink_to_credentials_fails_whole_backup`, `test_persona_hardlinked_to_ledger_fails_whole_backup_no_leak`, the other four ledger-hardlink tests) are **unmodified and still pass** — the identity-check-before-nlink-check ordering preserves their exact `match=` assertions.

**Live adversarial replay (outside pytest):** reproduced the literal rotation scenario — resolve `forbidden_identities` for credentials (inode A), rotate `credentials.json` to a genuinely new inode (verified via `os.rename` over a freshly-written file, confirmed A≠B), hardlink a persona to the rotated file, then call `_open_state_bearing` directly with a **deliberately stale** forbidden set that only knows inode A (simulating "already resolved, rotated during collection"). Result: `kind='hardlink'`, blocked — proving the fix closes the gap independently of whether the specific rotated identity happens to be known to `forbidden_identities` at all. Repeated identically for `ledger.db` rotation (via `os.replace` to guarantee a new inode, confirmed old≠new). Both blocked, no leak.

**Remaining limitation:** honestly documented, not hidden — this is a *v1, single-process, POSIX-`st_nlink`* invariant. It cannot detect a hardlink created on a filesystem that doesn't support hardlinks meaningfully reporting `st_nlink` (irrelevant for Lumina's supported Linux/macOS targets). It does not (and is not intended to) detect a **copy** of a state file's bytes placed at a forbidden identity by other means — that class is unaffected by this fix and remains covered entirely by the existing forbidden-identity content boundary elsewhere in the module.

### B2 — Stable descriptor does not mean stable bytes (BLOCKER)

**Root cause:** A2F5's `_open_state_bearing` proves a descriptor is safely opened (not a symlink/special file, not forbidden, now not a hardlink) from **one** `fstat`, then the caller reads its bytes **once**. A2R6 proved this is insufficient: a concurrent writer holding the same inode open can mutate it *during* that single read — truncate, append, overwrite the beginning/middle/end, or perform a byte-for-byte **size-preserving** rewrite — and the reader can capture a torn, hybrid byte sequence that remains syntactically valid (e.g. still-parseable JSON stitched from two different real versions) and therefore passes every downstream check unchanged. A size/mtime-only staleness check is provably insufficient (a size-preserving rewrite defeats size; a sufficiently fast rewrite can in principle land within the same mtime tick on some filesystems) — the fix has to compare full stat identity **and** prove content repeatability.

**Repair — bracketed double-read, bounded retry:** new primitives at [`core/agent_backup.py:900-978`](core/agent_backup.py:900):
- `_read_fd_fully_keep_open(fd)` — like the existing `_read_fd_fully`, but does not close `fd` (needed to read it a second time).
- `_stability_tuple(st)` — `(st_dev, st_ino, st_mode, st_nlink, st_size, st_mtime_ns, st_ctime_ns)`.
- `_read_stable_bytes_or_none(fd)` — `fstat A → read bytes_1 → fstat B → seek(0) → read bytes_2 → fstat C`. Returns `(bytes_1, True)` **only** if `stability_tuple(A) == B == C` **and** `bytes_1 == bytes_2`; otherwise `(None, False)`. Always consumes and closes `fd` (mirrors `_read_fd_fully`'s ownership contract).

[`core/agent_backup.py:1175-1244`](core/agent_backup.py:1175) `_stage_required_state_file` was rewritten around this: on an unstable read, it does **not** retry the same descriptor — it closes it and calls `_open_state_bearing` again, a **brand-new secure open** (Section 11's explicit ask), bounded to `_MAX_STABLE_CAPTURE_ATTEMPTS = 2` total attempts. A recovered mutation is recorded truthfully in the manifest's `warnings[]` (never silently absorbed); an unstable result on the final attempt raises `AgentBackupError` — fail the whole backup, never publish a torn read, regardless of whether it happens to look syntactically valid.

A useful defense-in-depth property, not separately engineered but true by construction: even a hypothetical mutation that perfectly disguised its stat metadata (not achievable without deliberately restoring `mtime`/`ctime`, itself requiring privileged/owner access already assumed out of scope) would *still* be caught by the `bytes_1 == bytes_2` content comparison alone, since the second read happens strictly after any mutation that occurred between the two reads.

**Never layered onto SQLite** (Section 10, explicit): `_snapshot_sqlite` is untouched; static test confirms its source never references either new primitive. Existing semantic validators (`_verify_prefs_payload`, the SQLite role-schema fingerprints) are unchanged — Section 13's "do not assume valid JSON implies coherent state" is satisfied by capture-time stability, not by broadening those validators.

**Regression:** parametrized `test_persona_same_inode_mutation_race_never_produces_hybrid_bytes` (all six mutation shapes: truncate, append, overwrite-begin/middle/end, size-preserving rewrite), `test_persona_repeated_mutation_exhausts_bounded_retry_and_fails_backup` (proves the retry is truly bounded), and one representative mutation each for `test_skill_same_inode_mutation_race_recovers_via_bounded_retry`, `test_custom_tool_same_inode_mutation_race_recovers_via_bounded_retry` (+ its own exhaustion test), `test_pending_actions_json_same_inode_mutation_race_recovers_via_bounded_retry`, `test_project_chats_json_same_inode_mutation_race_recovers_via_bounded_retry`, `test_project_binding_json_same_inode_mutation_race_recovers_via_bounded_retry`, `test_prefs_json_same_inode_size_preserving_mutation_race_recovers` (deliberately uses the size-preserving mutation, since prefs.json content is independently JSON-validated at verify time and truncation would conflate two different failure modes). Every recovery test compares the archived bytes against the actual final on-disk bytes (never merely "looks plausible") and asserts a truthful `warnings[]` entry. Matches this test suite's own established convention (see the A2F5 note's hardlink-matrix table) of proving the mechanism generically across a representative subset rather than exhaustively multiplying near-identical test bodies for every file × every mutation combination — the primitive is the same code path for every caller, by construction (`_stage_required_state_file`'s own callers, all routed through it).

**Live adversarial replay (outside pytest):** live truncate-mid-read race against a real `build_agent_backup` call (via `os.open`/`_read_fd_fully_keep_open` hooks correctly targeting only the racing file's own descriptor) — confirmed the archived bytes exactly equal the final on-disk (mutated) content, never a hybrid, and the recovery warning was recorded.

**Remaining limitation:** the bounded retry is exactly that — bounded. A source under **sustained**, continuous mutation (not a single race window, but a writer that never settles across two full attempts) will fail the backup, by design (per Section 11's own "if still unstable: fail backup", not "wait indefinitely"). This is the correct v1 behavior, not a limitation to fix later, but it is honestly a scenario where an operator retrying the whole backup command may need to retry more than once if the source is pathologically hot.

### B3 — Build receipt evidence could transfer to a replacement archive (BLOCKER)

**Root cause:** `build_agent_backup_with_receipt` called `build_agent_backup` (which builds archive A, verifies it, publishes it via `os.replace()`, and returns **only** a manifest — its own build-time evidence already discarded), and **only after that call had fully returned** separately reopened `dest_path` **by name** (`_read_archive_bound_once`) to compute the receipt's hash/size. AGENT-BACKUP-RESTORE-A2R6 proved live: replace `dest_path` with a different, independently verifier-valid archive B in the gap between "build returns" and "receipt reopens the path", and the receipt described B while still asserting A's own build-time security evidence.

**Repair — one internal build result, no reopen left to race:** [`core/agent_backup.py:2589-2624`](core/agent_backup.py:2589) `_BuiltArchiveResult` (private) bundles `.manifest`, `.fd` (a descriptor opened on the built archive's own `tmp_path` inode **before** the publishing `os.replace()` — see [`core/agent_backup.py:2784`](core/agent_backup.py:2784) — so it is permanently immune to anything that later happens to the `dest_path` *pathname*), `.dest_path`, and `.published_identity`. [`core/agent_backup.py:2627`](core/agent_backup.py:2627) `_build_agent_backup_core` (private, renamed from the old public `build_agent_backup`) is now the **sole** implementation: it builds, verifies, opens+fstats `tmp_path` for evidence, replaces, and returns this result. The public `build_agent_backup` ([`core/agent_backup.py:2838`](core/agent_backup.py:2838)) is a thin wrapper that discards `.fd` unread; `build_agent_backup_with_receipt` ([`core/agent_backup.py:3792`](core/agent_backup.py:3792)) reads bytes **directly from `.fd`** (`_read_fd_fully`, which consumes and closes it) — there is no `os.open(dest_path, ...)` call anywhere in that call chain anymore for anything to race.

**Bind publication identity too (Section 18):** immediately after `os.replace()`, `_build_agent_backup_core` independently confirms — via a **separate** `os.lstat(dest_path)` call, never trusted from `os.replace()`'s own bare success — that `dest_path` still refers to exactly the inode just published (`lstat`, not `stat`, so a replacement-by-symlink is caught rather than silently followed). A mismatch (or the lstat itself failing) raises `AgentBackupError("destination changed before build receipt could be finalized ...")` — the exact preferred v1 wording the mission specified — and closes the held `built_fd` before propagating. This applies in the **shared core**, so both `build_agent_backup` and `build_agent_backup_with_receipt` get the protection, not only the receipt path.

**Arbitrary existing archive API remains non-attested** (Section 20, unchanged from A2F5): `build_backup_receipt(archive_path)`'s public signature still accepts only `archive_path`; `_BuildSecurityEvidence` still requires the module-private `_EVIDENCE_SENTINEL` to construct.

**Regression:** `test_build_evidence_cannot_transfer_to_a_replacement_archive_the_literal_a2r6_reproduction` (the literal reproduction: build A, race a marked, independently-valid decoy B into `dest_path` via a monkeypatched `os.replace` firing immediately after the real one lands, call `build_agent_backup_with_receipt` — now raises `"destination changed"` rather than ever returning a PASS receipt describing B), `test_build_agent_backup_plain_also_fails_closed_on_post_replace_tampering` (proves the shared-core protection covers the plain, non-receipt call path too). All five pre-existing `_BuildSecurityEvidence`/receipt-forgery tests from A2F5 (`test_build_agent_backup_with_receipt_honestly_proves_build_time_boundary_check`, `test_build_backup_receipt_public_signature_has_no_evidence_parameter`, `test_hand_built_archive_cannot_forge_build_evidence_via_public_receipt_api`, `test_build_security_evidence_cannot_be_constructed_outside_the_module`, `test_build_evidence_reuse_across_different_archive_is_rejected`) are **unmodified and still pass** — `test_build_evidence_reuse_across_different_archive_is_rejected` specifically still calls the *public* `build_agent_backup` directly and constructs `_BuildSecurityEvidence`/`_build_receipt_from_bytes` by hand, confirming the public surface's exact shape is unchanged. The two pre-existing inode-replacement receipt tests (`test_receipt_hash_size_verify_bind_to_one_open_despite_pathname_replacement`, `test_receipt_survives_inode_replacement_via_atomic_rename_after_open`) — which attack `build_backup_receipt`'s own `_read_archive_bound_once`, a genuinely different, still-necessary code path for arbitrary existing archives — are also unmodified and still pass.

**Live adversarial replay:** covered by the pytest reproduction above (run live against real `os.replace` sabotage, not a synthetic unit test of an isolated function) — confirmed `state["swapped"]` fired, confirmed `dest_path` genuinely held the decoy bytes afterward (proving the attack really landed), confirmed no PASS receipt was ever produced describing it.

**Remaining limitation:** the post-replace `lstat` check itself has a residual, honestly-documented window — between `os.replace()` returning and the `lstat()` call that follows it, both single syscalls in the same synchronous function with no Python-level yield point in between on the common path. This is not eliminable without OS-level transactional rename+verify (not available on POSIX), the same category of narrowed-not-eliminated residual limitation this module already documents for `_connect_sqlite_with_bound_identity`'s connect-time window (Section 3's "a Linux-specific A2 v1 implementation is acceptable if documented honestly").

### B4 — Closed-world dynamic families accepted impossible nested names (BLOCKER)

**Root cause:** every flat-overlay deriver (`_deriver_personas`, `_deriver_skills`, `_deriver_tool_profiles`, `_deriver_avatars`, `_deriver_voices`) and every Project sub-file deriver (`_deriver_project_binding`, `_deriver_project_chats`, `_deriver_project_md`, `_deriver_codebase_md`) only checked a suffix or bare truthiness on the extracted, user-controlled component — never that it was a single, real path *segment*. `_collect_overlay_dir` enumerates each family via a **flat** `os.listdir()` (never a walk); `_project_dir_names` similarly lists only flat, single-segment directory names — neither can *ever* physically produce a `'/'`-separated value. AGENT-BACKUP-RESTORE-A2R6 proved live that a hand-built manifest with `logical_id='overlay.personas.nested/evil.json'`, `archive_path='overlay/personas/nested/evil.json'` (and the equivalent `overlay.projects.parent/child.binding_json` shape) still passed `_is_recognized_member`, because the OLD deriver faithfully reconstructed exactly the archive_path the hostile manifest itself declared — the bijection check was correct in form but validated against a deriver that itself accepted an impossible input.

**Repair — a single choke-point segment-safety check:** [`core/agent_backup.py:429-459`](core/agent_backup.py:429) `_is_safe_leaf_name(name)` rejects `'/'`, `'\'`, NUL, and exactly `'.'`/`'..'`; permits everything else — spaces, multiple dots, Unicode, mixed case, legal punctuation (Section 23/26: dots are not separators inside a user-controlled name; only the derivers' own fixed prefix/suffix boundaries are). Wired into all nine affected derivers' own guard conditions. **Deliberately not applied** to `_deriver_custom_tools`: `_collect_custom_tool_members` uses `_safe_walk` (a real recursive tree — the existing `_pending/staged_tool.py` example is a genuinely legitimate nested collector output), so restricting it to a single segment would reject real archives. General path-traversal segments (`'..'`, an empty segment) inside a legitimately-nested custom-tool relpath are already rejected elsewhere, uniformly for every family, by `_check_path_and_identity_rules` against the final `archive_path` itself (unchanged) — this is why custom_tools didn't need (and doesn't get) the same fix: it was never the vulnerable case.

**Regression:** `test_verify_rejects_impossible_nested_persona_the_literal_a2r6_reproduction`, `test_verify_rejects_impossible_nested_project_binding_the_literal_a2r6_reproduction` (both literal reproductions, including a receipt-FAIL confirmation for the persona case), parametrized `test_verify_rejects_impossible_nested_names_across_every_flat_and_project_family` (skills, tool_profiles, avatars, voices, chats_json, project_md, codebase_md, plus the degenerate `'..'`-as-extracted-name case), `test_legitimate_weird_names_still_pass_through_the_real_collector` (Section 25/26: built through the **real** collector, never hand-rolled — spaces, dots, Unicode, mixed case in both a persona filename and a Project name — confirms verifier language == collector language in *both* directions). `test_is_recognized_member_accepts_every_real_family_shape` (pre-existing, including its own dotted-project-name edge case) is unmodified and still passes, confirming the tightened derivers didn't regress any real shape.

**Live adversarial replay:** covered by the pytest reproductions (already a direct call against `verify_agent_backup`/`build_backup_receipt`, not a synthetic isolated check) — confirmed `report["valid"] is False` and `receipt["verification"] == "FAIL"` for the literal persona reproduction, never an inflated PASS.

**Remaining limitation:** none identified for this specific finding — the fix is a closed-form segment check with no partial/probabilistic behavior.

## The two new v1 architectural rules (Section 36, explicit)

1. **State-bearing plain files must have `st_nlink == 1`.** Checked on the already-opened, already-fstat'd descriptor inside `_open_state_bearing`, after the existing forbidden-identity check. Applies to every REQUIRED, discovered, state-bearing member captured via `_stage_required_state_file` (persona, skill, tool_profile, avatar, voice, custom tool, tool_audit.log, pending_actions.json, pending_actions_audit.log, Project projectlist.md/project.md/binding.json/chats.json, prefs.json). Deliberately **not** applied to the lenient `_open_verified` path (optional members: identity_trailers.json, codebase.md) or to SQLite sources (their own already-hardened connection-identity mechanism is untouched and out of scope). This closes the entire hardlink-alias class categorically, rather than reactively widening a blacklist of specific forbidden identities that can only ever describe what was already known at snapshot time.

2. **State capture requires stable descriptor metadata + repeatable bytes**, not merely a safely-opened descriptor. `_read_stable_bytes_or_none`'s bracketed double-read (fstat → read → fstat → seek(0) → read → fstat, requiring all three stat snapshots to agree on device/inode/mode/nlink/size/mtime_ns/ctime_ns **and** both reads to produce byte-identical content) is the shared primitive; a detected instability retries once from a brand-new secure open (never the same suspect descriptor), and a still-unstable result fails the whole backup rather than ever publishing a torn/hybrid read. Never applied to SQLite sources, which have their own point-in-time-consistent snapshot mechanism (the online backup API) that this primitive is not a replacement for.

Both rules are intended as durable, future Restore/Backup invariants — any future collector added to this module should route through `_stage_required_state_file` (which already enforces both) rather than reimplementing capture directly.
