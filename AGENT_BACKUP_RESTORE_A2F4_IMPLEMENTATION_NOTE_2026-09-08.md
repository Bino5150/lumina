### R4-B1 — SQLite identity proof was process-wide, not connection-specific (BLOCKER)

**Root cause:** A2F3's `_connect_sqlite_with_bound_identity` proved `expected_identity`/`credentials_identity` by checking whether either appeared **anywhere** in a single static listing of every file descriptor this *process* currently held open — not specifically among the descriptors *this* `open_fn()` call itself acquired. A2R4 exploited exactly that: park an unrelated, already-open connection resting on the expected inode, then let the connect under test actually open attacker-selected (non-credentials) bytes at a different inode. The resting connection supplied "expected identity present somewhere," the attacker's own new fd never touched `credentials_identity` either, and the process-wide membership check waved the whole thing through even though the connection being verified never touched the expected inode at all.

**Repair:** [core/agent_backup.py:777-995](core/agent_backup.py:777) — `_proc_fd_identity_snapshot()` takes an identity-keyed `{fd_number: (dev, ino)}` snapshot; `_newly_acquired_identities(before, after)` computes the set of identities whose `(fd_number → identity)` binding is new *or changed* between two snapshots (not a bare fd-number-presence diff, which is provably insufficient on its own — see below); `_connect_sqlite_with_bound_identity` now takes a `before` snapshot, calls `open_fn()`, takes an `after` snapshot, and examines **only** `_newly_acquired_identities(before, after)` for the credentials-reject and expected-require checks. A pre-existing, already-open connection — resting on the expected inode, the credentials inode, or anything else — is excluded from consideration entirely, regardless of what it happens to be resting on, because it is present unchanged in both snapshots. The whole before/after pair for one call is taken under a new module-level `_SQLITE_CONNECT_SERIALIZE_LOCK` (`threading.Lock`), so this module's own concurrent invocations (if any future caller ever snapshots two databases from separate threads) cannot interleave their own snapshots with each other.

**Why identity-keyed, not name-keyed, diffing:** A first attempt at before/after diffing (rejected, not shipped) compared bare fd-*number* sets. That is insufficient: if an unrelated fd number is closed and immediately reused (by completely unrelated code) for a different file between the two snapshots, comparing number sets alone sees "same name, nothing new" and silently misses the identity change. `_newly_acquired_identities` closes this by keying on `(fd_number, identity)` pairs — a number is excluded from the result only if it existed before bound to the *exact same* identity it has after.

**Honest residual limitation, documented in the function's own docstring:** the before/after pair is serialized against *this module's own* other calls only. It cannot and does not claim to serialize every fd-opening/closing code path elsewhere in a live, multi-threaded Lumina process — a coincidental, unrelated same-process activity that happens to open a *new* fd bound to `expected_identity` during the exact connect() window would be indistinguishable from this call's own fd. This is an accepted, honestly-recorded limitation of a userspace-only, non-cryptographic, Linux-`/proc`-based v1 identity proof (the mission's own "a Linux-specific A2 v1 implementation is acceptable if documented honestly"). It does **not** reopen A2R4's own reported gap, which required an unrelated connection resting on the expected inode *before* the call began — that is unconditionally excluded now.

**Focused regression:** `test_newly_acquired_identities_detects_fd_number_reuse_not_just_new_numbers` (direct, deterministic proof of the diffing primitive), `test_connect_sqlite_unrelated_resting_connection_on_expected_inode_is_not_a_hall_pass` (the exact Goblin reproduction), `test_connect_sqlite_unrelated_resting_connection_on_other_inode_does_not_block_legitimate_connect` (no false positive), `test_connect_sqlite_multiple_unrelated_connections_still_identifies_correctly`, `test_connect_sqlite_wal_mode_extra_descriptors_still_identify_correctly`, `test_connect_sqlite_survives_concurrent_unrelated_fd_churn`, `test_connect_sqlite_with_bound_identity_survives_source_deleted_immediately_after`, `test_connect_sqlite_with_bound_identity_fails_closed_when_proc_fd_unreadable` (new, distinct from the pre-existing "`/proc` unavailable" test). The two pre-existing connect-time hardlink-swap-and-restore regressions (`test_sqlite_connect_time_hardlink_swap_and_restore_still_caught`, `..._flight_recorder_still_caught`) still pass unmodified, confirming the rewrite did not regress A2R3's own original attack.

**Self-adversarial (live, outside pytest):** reproduced the exact Goblin attack (unrelated connection resting on the expected inode; the tested connection actually opens attacker bytes at a different inode) directly against `_connect_sqlite_with_bound_identity`. **Blocked** — `AgentBackupError: could not prove...`. Separately confirmed, by running the *old* A2F3 process-wide-membership logic side-by-side against the identical attack setup, that the old code **wrongly accepted** the same attack (returned a live connection to the attacker's file). See `adversarial_pass_a2f4.py` §1 below.

### R4-B2 — Discovered required state could still vanish through symlink/special-file paths (BLOCKER)

**Root cause:** A2F3's own policy (documented in the code at the time) deliberately treated a symlink discovered at a state-bearing position as "exclude with a warning, never escalate" — reasoning that a hostile or accidental symlink must never be able to permanently deny a backup. A2R4 showed this reasoning is no longer acceptable at v1: a custom-tool `.py` symlink, a Project `chats.json` symlink, and (separately) a `tool_audit.log` FIFO all still produced a **published, complete-looking** backup with that specific state silently absent. `tool_audit.log`/`pending_actions.json`/`pending_actions_audit.log` were not checked for a special-file/symlink substitution *at all* before staging began (they were only ever run through `os.path.exists()`, which itself both follows symlinks and returns `False` for a *broken* symlink — silently treating a broken-symlink substitution as ordinary absence).

**Repair:** [core/agent_backup.py:654-696](core/agent_backup.py:654) — `_reject_if_special_file()` is rewritten as `_reject_if_special_file_or_symlink()`: it now raises `AgentBackupError` (`SECURITY_REJECTED_STATE`) for **either** a non-regular special file (FIFO/socket/device, as before) **or** a symlink (new), for anything that `lstat`s successfully at a state-bearing expected filename. Wired into every discovered-required-state position that previously either lacked this check or only excluded-symlinks-with-a-warning:
- `_collect_custom_tool_members`'s per-file walk loop (was already calling the old function; now gets the stricter symlink behavior automatically) — [core/agent_backup.py:1549](core/agent_backup.py:1549).
- `_collect_overlay_dir`'s per-file loop (personas/skills/avatars/voices/tool_profiles) — the old two-branch "warn-and-continue for symlink, raise for special" is now one branch that raises for either — [core/agent_backup.py:1648-1662](core/agent_backup.py:1648).
- `_collect_audit_members`: **new** pre-checks for `tool_audit.log`, `pending_actions.json`, `pending_actions_audit.log` — none of these were checked here at all before this pass — [core/agent_backup.py:1576-1601](core/agent_backup.py:1576).
- `_collect_project_members`'s four Project-document `else` branches (`projectlist.md`, `project.md`, `binding.json`, `chats.json`) — renamed call sites, same stricter behavior. `codebase.md` is deliberately **not** touched — it remains `REBUILDABLE_GENERATED`/`required: false` per A1, exactly as the mission's Section 4 exemption specifies.

A plain-file trust-boundary violation discovered *after* this check passes (a directory-symlink escape, a hardlink aliasing the credentials store) is **not** escalated by this change — that remains the pre-existing, unchanged, "exclude just this one file with a warning" behavior inside `_open_verified`/`_stage_plain_file`, per the mission's Section 26 instruction to preserve "plain-file descriptor-bound security." The distinction is deliberate: `_reject_if_special_file_or_symlink` fires *before* staging even begins, asking "is this discovered, state-bearing position even capturable as bytes at all" — not "does this regular file's actually-opened descriptor pass the credentials/escape boundary check."

**This is a deliberate, explicit policy reversal from A2F3**, not an oversight being corrected quietly. Four existing tests encoded the old policy and were rewritten rather than deleted-and-forgotten:
- `test_symlink_to_credentials_excluded_not_leaked` → renamed `test_persona_symlink_to_credentials_fails_whole_backup`, now asserts `AgentBackupError` + no archive published.
- `test_credentials_never_required_to_be_excluded_at_full_backup_cost` → repurposed as `test_hardlink_alias_still_excludes_only_that_one_file_not_the_whole_backup` (a **hardlink**, not a symlink, is a genuine regular file at the `lstat` level and is *not* affected by this change — it is still caught only by the deeper, unchanged, descriptor-bound credentials-identity check, and that boundary violation correctly still excludes just the one file). This explicitly documents the surviving symlink/hardlink distinction rather than leaving a silently-obsolete test in place.
- `test_custom_tool_replaced_with_symlink_still_excluded_not_leaked` → renamed `test_custom_tool_replaced_with_symlink_fails_backup`, now asserts full failure.

**Focused regression (new):** `test_tool_audit_log_replaced_with_fifo_fails_backup`, `test_tool_audit_log_replaced_with_symlink_fails_backup`, `test_tool_audit_log_broken_symlink_fails_backup_not_treated_as_absent` (proves the broken-symlink/`os.path.exists()` gap specifically), `test_pending_actions_json_replaced_with_symlink_fails_backup`, `test_project_chats_json_replaced_with_symlink_fails_backup`, `test_project_chats_json_replaced_with_fifo_fails_backup`, `test_project_binding_json_replaced_with_symlink_fails_backup`, `test_projectlist_md_replaced_with_symlink_fails_backup`. Pre-existing FIFO/socket regressions for personas/skills/custom-tools are unchanged and still pass.

**Self-adversarial (live):** reproduced a custom-tool `.py` symlink and a `tool_audit.log` FIFO directly against `build_agent_backup`. Both **blocked** — `AgentBackupError`, no archive published. See `adversarial_pass_a2f4.py` §2/§3 below.

**Remaining, deliberately out-of-scope limitation, recorded honestly:** a symlinked *subdirectory* nested inside `custom_tools` (as opposed to a symlinked `.py` *file*) is still silently skipped from traversal by the pre-existing `dirs[:] = [d for d in dirs if ... and not os.path.islink(...)]` filter in `_collect_custom_tool_members`, unchanged by this pass — this was not among the specific reproductions A2R4 named (which were all file-level: a `.py` file, `tool_audit.log`, `chats.json`), and `test_symlinked_subdirectory_inside_custom_tools_not_traversed` (pre-existing, unchanged) still documents and locks in that specific behavior. Flagged here rather than silently left unaddressed, in case a future pass wants to extend Section 4's rule to directory-shaped discoveries too.

### R4-B3 — Dynamic manifest policy was still partially archive-authored (BLOCKER)

**Root cause:** A2F3's `_CANONICAL_MEMBER_POLICY` fixed values only for members with a *fixed* (non-parameterized) `logical_id`. Every *dynamic* (per-file, per-project) member family — `overlay.projects.<name>.binding_json`/`.chats_json`/`.project_md`/`.codebase_md`, `overlay.personas.<file>`, `overlay.skills.<file>`, `overlay.tool_profiles.<file>`, `overlay.avatars.<file>`, `overlay.voices.<file>` — had **zero** enforcement of `state_class`/`portable`/`restore_policy`/`rebind_policy` beyond the generic enum-membership check. Separately, `state.audit.pending_actions.json`/`pending_actions_audit.log` (fixed logical_ids) had no fixed-value policy *and* no field allowlist at all — an archive could freely attach `approved`, `autoexecute`, `destination_authority`, etc.

**Repair — fixed-value enforcement, generalized to dynamic families:** [core/agent_backup.py:292-330](core/agent_backup.py:292) `_DYNAMIC_MEMBER_POLICY_FAMILIES` is a `(prefix, suffix, fixed_fields)` table; `_validate_dynamic_member_policy()` ([core/agent_backup.py:2419-2445](core/agent_backup.py:2419)) matches every member against it by `logical_id.startswith(prefix) and logical_id.endswith(suffix)` and enforces the fixed fields regardless of archive claims. `content_kind` is deliberately **not** fixed for avatars/voices — their real content_kind legitimately varies by file extension (json/markdown/binary), unlike every other family. `overlay.projects.projectlist` and `metadata.identity_trailers`/`metadata.shipped_baseline_hashes` are *fixed* logical_ids and were simply added to the existing `_CANONICAL_MEMBER_POLICY` dict instead (Section 8's "at minimum define policy for... Project project.md... identity_trailers metadata").

**Repair — tight field allowlist, extended beyond custom-tools/tool-audit:** [core/agent_backup.py:253-291](core/agent_backup.py:253) — `_authority_bearing_allowed_fields_for(logical_id)` now also recognizes `state.audit.pending_actions.json`/`pending_actions_audit.log` (fixed logical_ids, `_FIXED_AUTHORITY_BEARING_LOGICAL_IDS`), `overlay.projects.<name>.binding_json` (dynamic, reuses `_AUTHORITY_BEARING_ALLOWED_FIELDS`), and `overlay.projects.<name>.chats_json` (dynamic, uses a **narrower** `_CHATS_JSON_ALLOWED_FIELDS = _AUTHORITY_BEARING_ALLOWED_FIELDS - {"rebind_policy"}` — Section 10's explicit "must not... declare machine binding," which `rebind_policy` as a field name specifically represents; chats.json's real v1 shape never carries one). `_validate_authority_bearing_member_schema()` was generalized to dispatch through this function rather than a hardcoded two-way `is_custom_tool`/`is_tool_audit` check.

**Repair — content survives, execution authority does not (Section 11's conservative contract, explicitly recorded per the mission's own instruction not to silently rewrite A1):** A1 does not name an explicit restore-authority rule for `pending_actions.json`/`pending_actions_audit.log` beyond "Overwrite" in Section C's table. Rather than inventing new policy language, this pass keeps the current implementation's own `restore_policy: "overwrite_atomic"` value as the fixed canonical policy (matching A1's own table exactly) and relies entirely on the tight field allowlist to foreclose authority-smuggling — since `overwrite_atomic` itself asserts nothing about execution authority, and no field in the allowlist (`logical_id`, `state_class`, `content_kind`, `archive_path`, `sha256`, `size`, `required`, `portable`, `restore_policy`, `rebind_policy`) can express `approved`/`autoexecute`/`destination_authority`/`owner_authorized`, a hostile manifest has no field left through which to assert execution authority at all. This matches A1's own Forward Notice ("restored *content* does not [need independent revalidation], restored *authority* claims [do]") without adding any new invented policy value.

**Focused regression:** parametrized `test_verify_rejects_project_binding_dynamic_policy_substitution` (`state_class`, `required`, `portable`, `restore_policy`, `rebind_policy`), parametrized `test_verify_rejects_project_chats_dynamic_policy_substitution` (`state_class=EXCLUDED`, `portable=EXCLUDED`, `restore_policy`), `test_verify_rejects_project_chats_autoexecute_field`, `test_verify_rejects_project_chats_machine_binding_field` (the `rebind_policy`-as-unrecognized-field case), parametrized `test_verify_rejects_pending_actions_authority_smuggling_field` (`approved`, `autoexecute`, `destination_authority`, `owner_authorized`, `restore_and_autoexecute`), `test_verify_rejects_pending_actions_audit_log_authority_smuggling_field`, parametrized `test_verify_rejects_pending_actions_fixed_policy_substitution`, `test_verify_rejects_persona_dynamic_policy_substitution` (representative proof the same mechanism covers the per-file overlay categories too), `test_verify_rejects_project_md_dynamic_policy_substitution`, `test_verify_rejects_identity_trailers_canonical_field_substitution`.

**Self-adversarial:** all of the above confirmed via the focused suite; the highest-risk cases (pending-actions authority smuggling, Project binding policy mutation) were the ones the mission's own Section 27 named explicitly and are covered by dedicated parametrized tests rather than a single example.

### R4-B4 — Build-time evidence and archive-self-assertion were conflated (BLOCKER)

**Root cause:** the receipt's single `canonical_credentials_store_excluded` field was derived correctly from the verified manifest's own exclusion record (a claim about *archive policy*), but nothing distinguished that from a claim about whether the *build-time filesystem/inode credential-boundary checks actually ran* for this specific archive. A2R4 hand-built an archive asserting the canonical exclusion record, generated a receipt, and the receipt's single field could be (mis)read as proof the live boundary checks ran — they never did; only the archive's own bytes were ever consulted.

**Repair:** [core/agent_backup.py:3033-3080](core/agent_backup.py:3033) — the single field is split into two, with distinct, explicit semantics documented in `build_backup_receipt`'s own docstring:
- `archive_policy_credentials_excluded` (renamed from `canonical_credentials_store_excluded`, same derivation as before — provable from the archive's own verified manifest alone).
- `build_credentials_boundary_verified` — a **new**, separate field. `build_backup_receipt(archive_path)` alone (the existing, default call shape every current test and the module's own public contract uses) always reports the honest string `"not_provable_from_archive_alone"` — it has no way to know whether *this invocation* performed the build that produced the archive's bytes. A new convenience function, `build_agent_backup_with_receipt(data_dir, base_dir, dest_path, **kwargs)` ([core/agent_backup.py:2978-2993](core/agent_backup.py:2978)), is the **only** code path that may honestly pass `build_credentials_boundary_verified=True` — it does so immediately after its own `build_agent_backup()` call has actually run the live filesystem/inode boundary checks against the exact archive just published, in this exact process, in this exact invocation. No signature/attestation mechanism was invented (out of scope, per the mission's explicit instruction); an honest "not provable" is the correct answer for every archive received from anywhere else.

**Focused regression:** `test_backup_receipt_fields_are_real_not_fabricated` (updated to assert both the renamed field and the new honest default), `test_build_agent_backup_with_receipt_honestly_proves_build_time_boundary_check` (new — the one path that may assert `True`), `test_backup_receipt_credential_exclusion_derives_from_manifest_not_hardcoded` (renamed reference only, same underlying assertion).

**Self-adversarial (live):** hand-built an archive (bypassing `build_agent_backup` entirely — direct `zipfile.ZipFile` construction) asserting the canonical credentials-exclusion record, then called `build_backup_receipt()` on it directly. **Blocked from over-claiming** — `verification=PASS`, `archive_policy_credentials_excluded=True` (correctly, provably true from the archive's own bytes), `build_credentials_boundary_verified='not_provable_from_archive_alone'` (correctly refuses to claim build-time evidence that was never generated). See `adversarial_pass_a2f4.py` §4 below.

### R4-B5 — Receipt verify→hash/size pathname race (BLOCKER)

**Root cause:** `build_backup_receipt` called `verify_agent_backup(archive_path)` (which opens the path itself, internally, then closes it) and *then* separately called `_sha256_file(archive_path)`/`os.path.getsize(archive_path)`, each **reopening the path by name a second time**. A2R4 exploited the gap: verify a genuinely valid archive, replace the pathname with a different file before the hash/size calls run, and the receipt reports `PASS` with hash/size describing the *replacement*, not what was actually verified.

**Repair:** [core/agent_backup.py:2948-2965](core/agent_backup.py:2948) — `_read_archive_bound_once(archive_path)` opens the path with a single `os.open()` call and reads the complete byte string through the descriptor that call returns — the same fd-binding technique `_connect_sqlite_with_bound_identity` and `_open_verified` already use elsewhere in this module for the identical class of problem: once `os.open()` succeeds, the descriptor is permanently bound to whatever inode existed at that instant, immune to any later rename/replace of the pathname used to open it. `build_backup_receipt` now reads the archive exactly **once**, hands those same bytes to `_verify_agent_backup_inner()` via `io.BytesIO(data)` (that function already only ever used its argument as `zipfile.ZipFile`'s own constructor argument, so it transparently accepts either a path or a file-like object — no signature change needed beyond a docstring clarification and a parameter rename for honesty), and derives `archive_sha256`/`archive_size` from the *same* `data` variable. Verify, hash, and size now all describe one single, immutable capture of the archive, taken at one instant, with zero reopen-by-name anywhere in the sequence.

**Focused regression:** `test_receipt_hash_size_verify_bind_to_one_open_despite_pathname_replacement` (remove+rewrite the pathname immediately after the one real `os.open()` succeeds — receipt still describes the original bytes), `test_receipt_survives_inode_replacement_via_atomic_rename_after_open` (a distinct mechanism — `os.replace()` swaps the pathname's underlying inode entirely rather than truncating in place). A symlink-pathname-replacement variant was considered and deliberately not added as a third near-duplicate test: the fix's invariant (never reopening the path by name after the first `os.open()`) makes the specific nature of whatever later occupies the pathname irrelevant — the two mechanisms already tested (in-place rewrite, atomic rename) already exercise the two structurally distinct ways a pathname's target can change out from under an fd.

**Self-adversarial (live):** confirmed via the two focused tests above, run live as part of the normal pytest collection (not a separate outside-pytest script, since the mechanism is deterministic and doesn't depend on `/proc` timing the way the SQLite fix does) — sabotage confirmed fired in both, receipt confirmed describing the *original*, not the replacement, bytes.

### R4-H1 — Baseline accepted an older real repository commit (HIGH)

**Root cause:** `_verify_baseline_against_git` proved `git_commit` resolves to *some* real commit reachable in the checkout, and that every claimed hash matches *that commit's own* blobs — but never that `git_commit` is the checkout's **current** release identity. A genuinely real, internally-self-consistent *older* (or otherwise different) commit's baseline therefore still passed, letting a stale snapshot misclassify overlay files legitimately changed since as `shipped_baseline_unmodified`.

**Repair:** [core/agent_backup.py:1198-1225](core/agent_backup.py:1198) — after the existing `cat-file -e` resolvability check, a new check resolves this checkout's actual current HEAD live via `git -C base_dir rev-parse HEAD` and requires `git_commit == current_head` exactly. "The trusted current release commit used by the running application" is never hardcoded — it is derived from `base_dir` itself, at verification time, matching the mission's explicit "do not hardcode that SHA" instruction. A dirty working tree does not affect this check (HEAD identity is independent of uncommitted edits sitting on top of it) — confirmed by a dedicated regression, not merely asserted.

**Packaged/no-git installation:** unchanged — `_verify_baseline_against_git`'s existing `not os.path.isdir(os.path.join(base_dir, ".git"))` early return already produces the correct "provenance = unknown + warning" fallback via `_load_baseline_hashes`; this pass adds no new signing/packaging machinery, per the mission's explicit "do not turn A2F4 into a signing/packaging campaign."

**Current baseline artifact re-verified (Section 22):** `metadata/shipped_baseline_hashes.json`'s own `git_commit` field already equals `ee40259c980d3c6fcca56fc2f27dcefd3814c178` — the exact current release HEAD confirmed in the Section 0 gate above — so the new HEAD-equality check does **not** invalidate the currently-shipped artifact; it continues to authenticate successfully (`test_baseline_valid_artifact_matching_current_release_is_trusted`, pre-existing, and the new `test_shipped_baseline_artifact_authenticates_through_full_load_path`, which additionally exercises the full `_load_baseline_hashes` path end-to-end rather than only the lower-level git-verification helper). `skills/rubber-duck-debugging.md` remains present, unchanged, captured, correctly classified `unknown` provenance (not in the shipped baseline, not shipped-baseline-unmodified) — no duck removal, no duck-related code touched.

**Focused regression:** `test_baseline_older_real_commit_not_current_head_falls_back_to_unknown` (the literal R4-H1 reproduction — every hash genuinely correct for an older commit, only HEAD has moved on), `test_baseline_dirty_working_tree_does_not_invalidate_matching_baseline`, `test_shipped_baseline_artifact_authenticates_through_full_load_path`. All pre-existing baseline regressions (`nonexistent_git_commit`, `different_real_commit` [a **different, more realistic** forgery — a real, *current* commit with stale hashes, which the pre-existing hash-mismatch check alone already caught and continues to catch, since that test's `git_commit` happens to already equal current HEAD], `hash_algorithm_not_sha256`, `tampered_file_hash`, `malformed_files_map`, `unknown_overlay_path`, `missing_git_metadata_context`) are unmodified and still pass.

## Design choices worth recording explicitly (not silent simplifications)

- **Section 18's `ArchiveVerificationEvidence`/`BuildSecurityEvidence` split** was offered as a "suggested conceptual separation," not a mandatory implementation. This pass achieves the same outcome the mission actually requires — build-time evidence and archive-self-assertion are never combined except where both are legitimately available — via two explicit, separately-derived receipt fields (`archive_policy_credentials_excluded`, `build_credentials_boundary_verified`) rather than introducing two new dataclasses for a receipt shape that is otherwise still a plain dict throughout this module. No behavioral gap results from this choice; it is a code-structure judgment call, recorded here rather than silently deviating from the suggested shape without comment.
- **Section 6's full special-file matrix for `tool_audit.log`** (FIFO, socket, symlink, disappears-after-discovery, unreadable) is exercised directly for FIFO, symlink, and broken-symlink (a stronger case than "disappears after discovery," since a broken symlink is present-but-unreadable-as-intended-content). A dedicated socket variant was not added as a fourth near-duplicate: `_reject_if_special_file_or_symlink`'s branch (`not stat.S_ISREG`) is identical code for a FIFO and a socket, and the mechanism generically is already proven separately for personas (`test_sole_persona_replaced_with_unix_socket_fails_backup`, pre-existing, unmodified). "Unreadable" (a permission-denied `tool_audit.log`) was not separately tested — the existing `_reject_if_special_file_or_symlink` only classifies by `lstat` shape (which succeeds regardless of read permission on the target), so a permission-denied-but-otherwise-regular file is not rejected by this specific check at all; it would instead surface later as a read failure inside `_stage_plain_file`'s own pre-existing `required=True` escalation path (unchanged, unmodified by this campaign, so not re-verified here beyond what the pre-existing `test_required_custom_tool_disappearing_during_staging_fails`-style coverage already locks in for the general "required source becomes unreadable mid-staging" case).
