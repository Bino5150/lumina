## B1 — Three physical plain-file families bypass strict capture (BLOCKER)

**Root cause:** A2F6 wired the universal anti-hardlink/stable-capture boundary (`_open_state_bearing` + `_stage_required_state_file`) into every collector whose members are `REQUIRED_AGENT_STATE`. Three physical members — `overlay/projects/*/codebase.md` (`REBUILDABLE_GENERATED`), `metadata/identity_trailers.json` and `metadata/shipped_baseline_hashes.json` (both `USER_OVERLAY`/`required: False`) — were left on the **old, pre-A2F5 primitive**, `_stage_plain_file`: a single `_open_verified` call (its own separate, non-atomic `lstat()`-then-`open()` pre-filter) plus one unguarded `_read_fd_fully()`. No `st_nlink` check, no stability proof, no retry. This directly disproved the module's own claimed "universal physical-file boundary." As the mission's own framing put it: *"we declared a universal physical-file invariant while leaving three physical ingestion paths on the old single-read primitive."*

**Architectural repair, not three point-fixes:** `_stage_plain_file` is removed entirely — there is no longer any function in this module with "open a physical file → single read → archive it" semantics for ANY ZIP payload. [`_stage_required_state_file` is renamed to **`_stage_physical_state_file`**](core/agent_backup.py:1212) (the old name was itself part of the finding: calling it "required" invited exactly the belief that a non-required physical member could safely use something weaker). A new shared loop, [`_open_and_capture_stable_bytes`](core/agent_backup.py:1158), factors out the bounded-retry stable-capture logic so it can be reused both by `_stage_physical_state_file` (writing to the ZIP staging area) and — new in this pass — by the final publication-observation check (B2, below), which re-reads the *published destination* through the identical boundary.

`required` vs. `optional` is now **entirely the calling collector's own business** — decided solely by how the caller reacts to a `None` return (raise, for a position that must exist; skip the member, for one that need not). The primitive itself never treats absence as an error and never treats presence-with-a-security-problem as anything softer than a whole-backup failure, for *any* caller. This was already exactly how `tool_audit.log` (optional-in-practice, `REQUIRED_AGENT_STATE`-tagged) worked under the old "required" primitive — the fix generalizes that existing, already-correct semantic to every physical member rather than inventing a new one.

**The three families, migrated:**
- [`_collect_project_members`](core/agent_backup.py:2401): `codebase.md` now calls `_stage_physical_state_file` directly; the redundant discovery-time `os.path.isfile`/`os.path.islink` pre-check (a non-atomic shadow of the decision `_open_state_bearing` already makes atomically from the opened descriptor) is removed.
- [`_collect_metadata_members`](core/agent_backup.py:2456): both `identity_trailers.json` and `shipped_baseline_hashes.json` migrated identically, same pre-check removal.

**Regression:** thirteen new tests reproduce the full attack matrix (Section 5/8/9) independently against all three families — ordinary hardlink, credentials hardlink, ledger hardlink, **rotated**-credentials/ledger hardlink (proving the fix holds for these newly-migrated positions regardless of when the forbidden inode came into existence, not merely for the personas case A2F6 already proved), and a same-inode mid-read mutation race with bounded-retry recovery: `test_codebase_md_hardlinked_to_ordinary_file_fails_whole_backup`, `test_codebase_md_hardlinked_to_credentials_fails_whole_backup`, `test_codebase_md_hardlinked_to_ledger_fails_whole_backup`, `test_codebase_md_hardlinked_to_rotated_credentials_fails_whole_backup`, `test_codebase_md_same_inode_mutation_race_recovers_via_bounded_retry`, and the equivalent five/four for `identity_trailers`/`shipped_baseline_hashes`. Two pre-existing tests were **rewritten** because A2R7 supersedes what they asserted:
- `test_non_state_bearing_hardlink_to_credentials_still_excluded_not_leaked` → `test_optional_metadata_hardlink_to_credentials_now_fails_whole_backup`: a credentials hardlink at `identity_trailers.json` used to be excluded with a warning (the old lenient policy); it now fails the whole backup, identically to a persona.

## B2 — Build attestation remains transferable/stale under same-inode post-publication mutation (BLOCKER)

**Root cause, and why it's deeper than B1:** A2F6's own fix for AGENT-BACKUP-RESTORE-A2R6 bound receipt evidence to a file descriptor (`_BuiltArchiveResult.fd`) opened on the built archive's own inode *before* the publishing `os.replace()` — correctly closing the **path-level replacement** attack (a different inode swapped in at `dest_path`). AGENT-BACKUP-RESTORE-A2R7 proved this was still incomplete: A2F6's design opened that descriptor early but **deferred the actual read** to whichever caller wanted receipt evidence (`build_agent_backup_with_receipt`, invoked sometime after `_build_agent_backup_core` had already returned). A live file descriptor reflects its inode's **current** bytes at the moment it is read — not a frozen snapshot from the moment it was opened. A **same-inode in-place rewrite** (no `os.replace()`, no new inode at all — an ordinary `open(dest_path, "r+b")` followed by a write, same `dev`/`ino` throughout) landing in that deferred window would have been silently read as if it were the verified build, and the receipt would then honestly-looking assert `build_credentials_boundary_verified=True` for bytes that were never actually built or verified by anything.

This is the finding the mission itself calls out as the sharper one: *"A normal user-writable filesystem path cannot be guaranteed to still contain the same bytes 'at function return' against an arbitrary concurrent same-user writer. An inode is mutable; even a last-millisecond verification has another last-millisecond after it."* No amount of additional identity-checking machinery closes this — Section 18's own words, *"same dev/inode != same archive bytes,"* apply exactly here: A2F6's identity check would have reported a perfect match (the inode never changed), while the actual bytes underneath it had already been swapped.

**Architectural repair — evidence realized before publication, never re-derived after:** [`_BuiltArchiveResult`](core/agent_backup.py:2622) no longer carries a file descriptor at all. `.built_data` (the full archive bytes), `.built_sha256`, and `.built_size` are now plain, already-realized Python values — [read and hashed](core/agent_backup.py:2855) **eagerly, synchronously**, immediately after `verify_agent_backup(tmp_path)` succeeds and strictly **before** `os.replace()` even runs, while the bytes still live at a private, randomly-named staging path only this process knows. Once realized as a Python `bytes` object, no filesystem event anywhere can ever change them — this is what makes the attestation genuinely immutable, not merely harder to attack. `build_agent_backup` (manifest-only) and `build_agent_backup_with_receipt` (evidence-needing) both consume these same already-realized fields; neither reads anything from a path or a descriptor after the fact.

**Immutable build-artifact evidence (Section 13-14):** `_BuiltArchiveResult`'s fields — `built_sha256`, `built_size`, `manifest`, and (via the existing `_BuildSecurityEvidence`/sentinel mechanism, unchanged) build-security evidence — all refer to archive A, finalized before any mutable destination state can influence them. [`build_agent_backup_with_receipt`](core/agent_backup.py:4016) builds its receipt directly from `.built_data`/`.built_sha256`, never re-deriving anything from `dest_path`.

**Final publication observation, separated from build attestation (Section 16-18):** [starting right after the publishing replace](core/agent_backup.py:2899), *after* `os.replace()` publishes and the best-effort directory fsync runs, one final, as-late-as-practical re-read of `dest_path` — via the exact same universal capture boundary as every other physical source (`_open_and_capture_stable_bytes`: `O_NOFOLLOW` open, `st_nlink==1`, forbidden-identity check, `expected_identity` match against the built inode, AND the bracketed double-read stability proof, with its own bounded retry) — is compared **by content hash**, not merely inode identity, against `built_sha256`. A mismatch of either kind (a different inode, per A2F6's own already-proven check, **or** the same inode with different content, the specific gap this pass closes) raises `AgentBackupError` before a `_BuiltArchiveResult` is ever constructed at all — Section 17's "do not issue a successful build receipt." The resulting `publication_observation` dict (destination, observed hash, `matched_built_artifact: True`, an ISO timestamp) is surfaced on the receipt under a separate `"publication"` key — explicit, structured, and never folded into the historical build-security evidence fields, exactly as Section 16 requires. It is documented, in both the module docstring and `_build_receipt_from_bytes`'s own, as **an observation at a specific moment**, never a promise that `dest_path` remains that way afterward (Section 11/19) — this module does not claim, and cannot achieve, permanent immutability of a mutable, user-owned filesystem path against an arbitrary concurrent writer.

**Field semantics clarified, names retained (Section 15):** `archive_sha256`/`archive_size`/`verification` are used identically by both `build_backup_receipt` (an arbitrary, possibly pre-existing archive — these fields honestly mean "as observed when this call read it") and `build_agent_backup_with_receipt` (these fields describe the immutable built artifact, by construction, forever). Renaming them per-caller would have fragmented one receipt shape into two incompatible ones for no real gain, since `build_backup_receipt`'s own semantics were never ambiguous to begin with. Instead, `_build_receipt_from_bytes`'s docstring now states the precise semantics unequivocally: these fields always describe the exact bytes passed into that specific call, never a standing promise about a mutable path's future content — satisfying Section 15's explicit fallback ("If retaining existing names, document unequivocally...").

**Publication preservation / rollback (Section 26):** source-vetted directly — before this pass, a publication-observation failure left `dest_path` holding known-tampered, unattested bytes with **no way to recover** whatever good archive had been there before this build started (`os.replace()` had already overwritten it). [Right before the publishing replace](core/agent_backup.py:2866), the code now preserves a cheap reference to any pre-existing `dest_path` content via a hardlink (zero-copy — the same inode survives under a second name regardless of what the `dest_path` directory entry does afterward). If the final observation detects a mismatch, [the mismatch-handling branch](core/agent_backup.py:2933) attempts to restore that snapshot via `os.replace()`; success or failure is reported honestly in the raised error's own message (`"prior destination restored"` / `"prior destination could NOT be restored (...): its bytes are preserved at <path> for manual recovery"` / `"no prior destination existed to restore"` for a fresh install) — never silently. A bug caught during this exact implementation (an `UnboundLocalError` from referencing the rollback-snapshot variable in a generic exception handler before it was unconditionally initialized) was found by running the test suite immediately after writing the code, not assumed away — fixed by initializing the variable at the top of the function before any code that could raise.

**Trailing ZIP bytes (Section 20, folded into this same verification hardening pass):** Python's `zipfile` (like most ZIP readers) locates the End-Of-Central-Directory record by searching and neither complains about nor even notices bytes appended after a structurally complete, valid archive — a 23-byte trailing append passed this module's own strict verifier entirely undetected. [`core/agent_backup.py`](core/agent_backup.py) adds `_check_no_trailing_zip_bytes`, wired into `_verify_agent_backup_inner` before `zipfile.ZipFile` even opens the archive: a genuinely `build_agent_backup`-produced archive's raw byte length is always exactly `EOCD_offset + 22` with a zero-length comment (this module's own `zipfile.ZipFile(..., "w")` call never sets one), so any trailing data or non-empty comment is now rejected as outside Lumina's v1 format contract, not merely tolerated as legal-but-unused ZIP structure.

**Regression:** `test_build_evidence_cannot_survive_same_inode_content_mutation_before_receipt` (the literal, sharper A2R7 reproduction — an in-place rewrite, not a path replacement), `test_build_evidence_cannot_survive_same_inode_content_mutation_racing_the_observation_read` (the mutation timed to land *during* the publication observation's own bracketed double-read), `test_receipt_attests_only_built_bytes_never_the_currently_observed_destination` (Section 14/19: a successfully-returned receipt keeps describing A forever even after `dest_path` is mutated to B by something else entirely *after* the call returns — while a fresh, independent `build_backup_receipt(dest)` correctly reports B, proving the receipt object and the live filesystem path are properly decoupled, exactly matching Section 12's "Restore must reverify" framing), `test_publication_mismatch_restores_the_prior_good_destination` and `test_publication_mismatch_with_no_prior_destination_reports_honestly` (the rollback mechanism itself, both branches), `test_verify_rejects_trailing_bytes_appended_after_valid_archive`, `test_verify_rejects_zip_comment`, `test_verify_rejects_trailing_bytes_via_build_backup_receipt`, `test_check_no_trailing_zip_bytes_accepts_a_genuinely_clean_archive`. All pre-existing A2F6-era build-evidence tests (`test_build_evidence_cannot_transfer_to_a_replacement_archive_the_literal_a2r6_reproduction`, `test_build_agent_backup_plain_also_fails_closed_on_post_replace_tampering`, the five `_BuildSecurityEvidence` tests) are **unmodified and still pass** — the new content-based check is a strict superset of the old identity-only one, so every attack the old check caught is still caught, by the same observable error message pattern (`"destination changed"`).

**Live adversarial replay (outside pytest):** all of the pytest reproductions above were additionally run live via a standalone script (real `os.replace`/`os.open` sabotage against real `build_agent_backup_with_receipt` calls, not synthetic unit tests) — same-inode in-place rewrite blocked at two distinct timing points (immediately after `os.replace()`, and racing the observation's own read), trailing-ZIP-append rejected, credentials/ledger rotation against all three newly-migrated B1 families blocked, same-inode mutation races against all three recovered without hybrid bytes.

**Remaining limitation, stated honestly (Section 11, not hidden):** the final publication observation itself has a residual, irreducible window — between its own read completing and this function returning control to its caller, both single Python statements with no yield point on the common path, but not literally atomic at the OS level. This is not eliminable without an OS-level transactional rename+verify primitive Lumina does not possess (the same category of narrowed-not-eliminated residual limitation this module already documents for `_connect_sqlite_with_bound_identity`'s own connect-time window). Per Section 12, this is exactly why Restore must reverify the actual bytes it consumes rather than ever trusting a receipt's historical PASS status as proof of a file's present content — a contract this note pins explicitly for that future work, not something this pass attempts to solve by making the receipt's promise stronger than reality allows.

## The four load-bearing architectural statements (Section 32, explicit)

1. **Every physical plain-file payload uses ONE strict capture boundary.** `_stage_physical_state_file` (renamed from `_stage_required_state_file`) is now the only function in this module that stages filesystem bytes into the archive, for every member family without exception; `_stage_plain_file` is removed entirely.
2. **A build receipt attests the immutable bytes produced and verified by that build invocation.** `_BuiltArchiveResult.built_data`/`built_sha256`/`built_size` are realized eagerly, before publication, as plain Python values — never a file descriptor, never anything requiring a later filesystem read to resolve.
3. **Publication-path observations are time-bounded observations, not promises that a mutable filesystem path can never change.** The `publication` receipt key records what was observed, when — it is never folded into build-security evidence, and its absence of a guarantee about the future is stated explicitly in both code comments and this note.
4. **Restore must reverify the actual archive bytes it consumes.** No Restore implementation exists yet; this is pinned here as the load-bearing contract that implementation must honor — a receipt's historical PASS is never sufficient proof of a file's present bytes.
